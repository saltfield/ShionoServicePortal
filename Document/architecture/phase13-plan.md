# Phase 13 計画 — メール通知

## 目的

業務イベント発生時に、関係ユーザーの **個人 `email`** へメール通知する。  
プッシュ／Slack／組織代表アドレスへの送信は含まない。

## 合意ステータス

| 項目 | 決定 |
|------|------|
| 第1弾イベント | **A 全部**（チケット新着・返信／価格申請・決裁結果／強制PW変更） |
| 購読 | **オプトアウト必要**（種別ごとに OFF 可。既定は ON） |
| 宛先 | **ユーザー `email` のみ**（空なら送らない） |
| キュー | **compose に `queue` コンテナ追加**（`queue:work`） |
| 基盤 | Laravel Notification（Mail）＋ `ShouldQueue` |

## 組織代表アドレスについて（今回は対象外）

「組織の代表メール（BP／カスタマーの連絡先 email）へ送る」ケースの例:

| ケース | 説明 |
|--------|------|
| 請求書・帳票の送付 | 経理・総務の共有受信箱へ送る（個人アカウントに依存しない） |
| 契約関連の正式通知 | 組織としての受領証明・保管 |
| 担当者が未登録／email 未設定 | 個人宛ができないときのフォールバック |
| 一斉お知らせの BCC 的運用 | 組織窓口1通に集約 |

本フェーズでは **個人ユーザー通知**に限定する。代表アドレス送信が必要になったら、宛先解決（ユーザー vs 組織）を別フェーズで設計する。

## スコープ

### 含む（13）

| 領域 | 内容 |
|------|------|
| 基盤 | Notification 基底、From、失敗ログ、Mailpit 確認 |
| キュー | `Develop` に `queue` サービス、`deploy.md` 追記 |
| 購読 | `user_notification_preferences`（または同等）。種別キー＋ enabled。未行＝ON |
| チケット | 新着（起票で相手側）／返信（相手側の未読関係者） |
| 価格申請 | 申請→承認権限者／承認・却下→申請者 |
| 強制PW | 管理者が強制変更を設定した対象ユーザー |
| UI | アカウントメニュー「通知設定」＋各ポータルのユーザー編集「メール通知設定」 |
| テスト | Notification fake ＋ Feature |

### 含まない

| 項目 | 備考 |
|------|------|
| お知らせ一斉メール | 第2弾候補 |
| 契約ステータス／請求失敗メール | 第2弾候補 |
| ユーザー招待・初期PWメール | 別設計（トークン） |
| 組織代表アドレス送信 | 上記のとおり後続 |
| プッシュ／ブラウザ通知 | 対象外 |

## 通知種別キー（案）

| key | 既定 | 内容 |
|-----|------|------|
| `ticket.message` | ON | チケット起票・返信 |
| `contract.application` | ON | 価格申請の申請・決裁結果 |
| `security.password_force` | ON | 強制パスワード変更（**オプトアウト不可**） |

セキュリティ系は OFF にできない。`security.password_force` は常に送信。

## 宛先解決（概要）

| イベント | 宛先 |
|----------|------|
| チケット起票 | 受領側で閲覧可能なユーザー（権限＋公開範囲を既存ロジックに合わせる）。email あり・購読 ON |
| チケット返信 | 相手陣営の関係ユーザー（発行側／受領側）。自分自身には送らない |
| 価格申請 | `contract.approve` を持つ、スコープ内の承認者 |
| 決裁結果 | 申請者（申請ユーザー） |
| 強制PW | 対象ユーザー本人 |

同一イベントで同一ユーザーへ多重送信しない（ユニーク）。

## 受け入れ基準

1. A の各イベントで、email あり・購読 ON の関係者にキュー経由でメールが積まれる  
2. オプトアウトしたユーザーには業務通知が飛ばない（強制PWは除く）  
3. email 未設定ユーザーには送らず、理由がログに残る  
4. Mailpit で本文・件名・宛先を確認できる  
5. `queue` 未起動時の運用注意が deploy に書いてある
